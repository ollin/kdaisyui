## Context

See proposal.md — Why. What shapes the approach here:

- The scaffold on disk was generated by OpenSpec 1.7.0 (`openspec --version` → `1.7.0`). It is
  CLI output, not authored content, and will be regenerated by `openspec update` on future
  upgrades.
- The rules this project works under already exist, but in two places that are *not* the
  repository: a machine-local agent skill (`openspec-house-rules`) and AGENTS.md, which covers
  kdaisyui conventions but says nothing about the planning workflow.
- 1.7.0's `operations.apply|archive.guidance` is **advisory** — it is served to an agent at the
  right moment, it does not enforce anything. Enforcement stays with CI and review.

## Goals / Non-Goals

**Goals:**
- The planning workflow survives a clean checkout and is visible to every contributor.
- Project-specific working agreements are stated *in the repository*, once.
- The repository carries integrations for the tools actually in use, and nothing else.

**Non-Goals:**
- Enforcing the guidance mechanically. `operations.guidance` is advisory by design; turning
  any of it into a gate is CI work, not this change.
- Editing the global `openspec-house-rules` skill — it lives outside this repo.
- Any change to `.opencode/skills/openspec-*` content. Those are CLI output; editing them
  guarantees a conflict on the next `openspec update`.

## Decisions

### 1. Split by portability, not by topic

The obvious move — copy the house rules into `config.yaml` — would duplicate them, and
duplicated rules drift. The boundary is instead **portability**:

| Lives in | What | Why |
|---|---|---|
| `openspec/config.yaml` | Facts and rules true *of this repository*: generated vs. hand-written sources, `io.github.ollin.kdaisyui`, `gradle.properties` as sole version source, the four modules, no release automation, what "green" means **here** (`:lib:test` + `:e2e-tests:test`, Playwright, in-process Ktor server) | A contributor cloning kdaisyui needs these and cannot get them anywhere else |
| global agent skill | Cross-project habits: Arlo notation mechanics, the ask-Oliver gate, issue mirroring conventions | Identical in every repo; copying it into each one is the drift |

Concretely: `config.yaml` says *"the full suite includes `:e2e-tests:test`; a scoped run is not
green"*. It does **not** restate what an Arlo prefix means.

*Alternative considered:* put everything in `config.yaml` for self-containment. Rejected — it
duplicates ~200 lines that change centrally, and the copy in this repo would silently age.

### 2. Remove the GitHub Copilot integration entirely

Copilot is no longer used. The uncommitted `README.md` edit that drops the Copilot row from
the AI-context table is therefore correct as written, and the repository should follow it
rather than the other way round.

`openspec init` offering "GitHub Copilot" as pre-selected was **not** evidence of use: it
detects the tool by the presence of a `.github/` directory, which this repo has for its CI
workflows. Every repository with GitHub Actions triggers that detection.

Three paths go, and only these three — everything else matching `copilot` lives in the
`daisyui/` submodule and is not ours:

- `.github/copilot-instructions.md` (tracked — delete)
- `.github/prompts/` (untracked, six `opsx-*.prompt.md` — never commit)
- `.github/skills/` (untracked, six `openspec-*` skill copies — never commit)

`.github/workflows/` is unaffected.

This also removes a maintenance trap: copilot-instructions.md#L28-L30 asserts that a normal
Gradle build regenerates components, which `commit-generated-sources` is about to make false.
Deleting the file retires the claim instead of obliging a later change to correct a document
nobody reads.

*Alternative considered:* keep the file as a generic entry point for any GitHub-side agent.
Rejected — it duplicates AGENTS.md, and an unused duplicate is exactly the kind of document
that goes stale unnoticed, as its build sentence already demonstrates.

### 3. This change uses `skip_specs: true`

Committing tooling and writing documentation changes no system behavior. Writing a
requirement into `openspec/specs/` to satisfy `openspec validate` would put a false statement
into the project's source of truth. 1.7.0 introduced `skip_specs` for exactly this shape.

This also sets the precedent for the change after next: `codegen-to-kotlin` is a
behavior-preserving port whose correctness criterion is an empty diff — also a `skip_specs`
candidate.

## Risks / Trade-offs

- **Committed CLI output goes stale on the next `openspec update`.** → Accept and make it
  visible: the skills and prompt files are committed verbatim, never hand-edited, so a future
  update produces a clean, reviewable diff instead of a merge conflict.
- **Advisory guidance can be ignored.** → Accepted by design. The guidance reduces the chance
  an agent *forgets* the e2e layer; it cannot stop anyone who chooses to skip it. CI remains
  the enforcement point.
- **`config.yaml` grows into a second AGENTS.md.** → Keep it to what artifact authors need
  while planning. AGENTS.md stays the guide for writing code; `config.yaml` is the guide for
  writing changes, and links rather than repeats.
- **`openspec update` may re-create the Copilot files**, since the same `.github/` detection
  will fire again. → The drift is visible (new untracked files) rather than silent; if it
  recurs, pin the tool selection in OpenSpec's configuration instead of deleting repeatedly.
