## Context

Prose documentation cannot be generated; only the code inside it can be kept honest. The first
version of this design kept it honest by injecting snippets from `example-app`. Task 2.1 refuted
that premise (`findings.md` F1), and this design replaces it: the snippets stay in the Markdown
and the build compiles them there.

## Decisions

### 1. Compile in place, not inject

**Chosen:** the build extracts every `kotlin` fence from the prose documents and compiles it.

**Rejected: inject from `example-app`.** Only about 12 of 41 usage snippets have an honest home
there. The rest would be marked unverified, or `example-app` would grow code written only to be
quoted. Both leave most of the documentation as unchecked as it is today.

**Rejected: shorten the snippets and link to `example-app`.** Cheap, but a tutorial that cannot
be read straight through stops being a tutorial.

**What compiling in place gives up:** the e2e guarantee that a snippet's page renders. A snippet
that compiles can still give bad advice. Compiling proves the API it names exists, with those
parameters and those receivers, and that is what goes stale on a rename.

### 2. A module, with the extractor as tested production code

`:doc-snippets` has two source sets:

- `main`: the extractor, a plain Kotlin program. It reads the documents, finds the fences and
  writes one `.kt` file per snippet. It is unit-tested in `src/test`, so it sits under the same
  100% line and branch gate as the library (A3).
- `snippets`: generated by running `main`, and compiled against `:lib`, `:ktor-integration`,
  kotlinx.html and the Ktor server. `check` depends on its compilation.

**Rejected: the extractor in `buildSrc`.** Build logic is not covered by Kover here, and buildSrc's
tests do not run in `./gradlew build`, so the extractor would be the one untested program in the
repository. **Rejected: markdown-magic.** It needs Node on the `check` path and installs 71 packages
(18 MB) for what is a fence finder.

### 3. One file and one package per snippet

Each snippet becomes `snippets/<document>_L<line>.kt` in its own package. Tutorials redefine the
same function as it grows (`shellSidebar` at step 4 and again later), so a shared package would
make the documentation's own narrative a compile error. The file name and a header comment name
the document and the line of the fence, so a compile error points at the Markdown.

### 4. Markers are HTML comments above the fence

```markdown
<!-- snippet: skip - the 0.7.x API, shown for migration -->
```kotlin
```

An HTML comment renders as nothing on GitHub and in IDEs, so readers never see the machinery. The
first directives are `skip - <reason>` and a context directive for snippets that are not
statements inside a `FlowContent` builder. Their exact set is decided by task 1.1's measurement, not
here. **An unknown directive, or `skip` without a reason, fails the build**: a silent marker would
be how an unchecked snippet hides.

### 5. Runs in `check`, so there is no drift job

Nothing generated is committed. The snippet sources live under `build/`, so a stale snippet is a
compile error in `check`, locally and in CI's existing `unit-tests` job. The first plan's separate
drift job is not needed, and its open question (join `check` or not) is answered: join it, because
the extractor needs no Node.

## Risks / trade-offs

**Wrapping is a guess about context.** A snippet is a fragment, and the wrapper decides what
surrounds it. A wrapper that is too generous lets a wrong snippet compile. Mitigated by one
default and few explicit directives, each visible in the Markdown above its fence.

**Markers are noise in the source of the documentation.** They are invisible when rendered, and
each one carries its reason, which is information a maintainer otherwise lacks.

**Compile time.** About 70 small files on top of the build. Measured in task 4.1, not assumed.
