## ADDED Requirements

### Requirement: The public API surface has a committed baseline
The `lib` module SHALL carry a checked-in dump of its public API, produced by the build rather
than written by hand, so that any change to the surface appears as a reviewable diff in the same
commit as the change that caused it.

**Verified:** Kotlin 2.4.10 provides this without a new dependency. `kotlin { abiValidation { } }`
registers `updateKotlinAbi`, `checkKotlinAbi` and `internalDumpKotlinAbi` on `:lib`, and
`updateKotlinAbi` writes `lib/api/lib.api`. Confirmed by running both tasks; the mechanism and
the two compiler messages that established it are recorded in this change's `notes.md`.

#### Scenario: The baseline is regenerated by the build
- **WHEN** a contributor runs the dump task
- **THEN** the baseline file is rewritten from the compiled output
- **AND** no part of it is authored by hand

#### Scenario: Re-dumping is a deliberate act
- **WHEN** the public API has legitimately changed
- **THEN** updating the baseline is a separate, explicit command
- **AND** the updated baseline is committed alongside the change that caused it

### Requirement: A diverging API fails the build
The build SHALL fail when the compiled public API of `lib` no longer matches its committed
baseline, and that check SHALL run in CI on every pull request rather than only on a developer's
machine.

**Verified:** `checkKotlinAbi` inserts itself into `:lib:check` — `:lib:check --dry-run` lists
`:lib:internalDumpKotlinAbi` and `:lib:checkKotlinAbi`. **Assumed:** that CI runs it. *Wrong if:*
the workflow's `unit-tests` job invokes `./gradlew :lib:test koverVerify koverXmlReport` rather
than `check`, in which case the gate exists locally and never runs on a pull request. This is
checked and closed by task 4.2, and task 4.3 requires the job to have been *seen* to fail.

#### Scenario: An undeclared API change is rejected
- **WHEN** the public API of `lib` differs from the committed baseline
- **THEN** the check task fails
- **AND** the failure names the divergence

#### Scenario: The gate runs on a pull request
- **WHEN** a pull request changes the public API without updating the baseline
- **THEN** a CI job fails
- **AND** the pull request cannot be merged on that basis alone

### Requirement: What the check detects is stated honestly
The specification SHALL record both what the baseline diff catches and what it does not, so that
nobody relies on it for a guarantee it does not give.

It SHALL record that the check detects:

- the removal of a public declaration, including a single enum entry;
- any change to a function's JVM descriptor, including a change in the number or types of its
  parameters, on both the function and its synthetic `$default` overload.

It SHALL record that the check does **not** detect where in a signature a parameter was added,
because parameter names are not part of an ABI. Inserting a parameter mid-signature and appending
one produce the same diff.

**Verified by measurement**, both probes recorded in `notes.md`:
inserting `dummyProbe: Boolean = false` between `center` and `end` on `daisyTooltip` changed
`ZZZZZZZZ` to `ZZZZZZZZZ` in the descriptor of the function and of `daisyTooltip$default`;
deleting `TooltipVariant.Error` removed the line
`public static final field Error Lio/github/ollin/kdaisyui/components/TooltipVariant;`.

#### Scenario: A removed enum entry is caught
- **WHEN** a regeneration drops an enum entry from the public API
- **THEN** the baseline diff shows the entry's line removed
- **AND** the check fails until the baseline is deliberately updated

#### Scenario: A shifted parameter list is caught, without being localised
- **WHEN** a regeneration adds a parameter to an existing generated function
- **THEN** the baseline diff shows the changed descriptor
- **AND** the specification does not claim the diff identifies the parameter's position

### Requirement: A breaking change carries a migration note before release
A public API change identified as breaking SHALL have a **How to migrate** entry in `README.md`
before the release that ships it, and the release documentation SHALL treat the API check and
that entry as part of what "ready to tag" means.

**Verified:** `README.md` already carries a "How to migrate" section for 0.2.0, written after the
fact, which is the shape the rule generalises. **Assumed:** that this remains a documented rule
rather than an automated one. *Wrong if:* a release ships a breaking change without the entry,
which would show that a rule nothing enforces is not a rule.

#### Scenario: A reader of a breaking release can act on it
- **WHEN** a release removes or changes a public declaration
- **THEN** `README.md` explains what to change at the call site
- **AND** the entry exists before the tag is pushed, not after

## Scope

The baseline covers `lib` only. `ktor-integration` is also published, but its public API is
hand-written and small, so a change to it is already a change somebody decided to make. The
hazard this capability exists for is the opposite case: `lib`'s API is generated from DaisyUI,
so a removal can arrive in a dependency bump that nobody reads. Extending the baseline to
`ktor-integration` is a later decision, not an omission.
