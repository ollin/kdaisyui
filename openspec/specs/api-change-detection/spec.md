# api-change-detection Specification

## Purpose
To make a change to `kdaisyui`'s published API impossible to ship without somebody having seen it.

The library's public surface is **generated** from DaisyUI and released automatically from a `v*`
tag, so the two moments where a human would normally notice a removal — writing it, and pressing
publish — do not exist here. v0.2.0 shipped a breaking change (`TooltipVariant.Neutral` removed,
because DaisyUI dropped `tooltip-neutral`) that nobody chose and no check caught; it was found by
a person reading a diff, and documented afterwards.

This capability replaces that reader with a committed baseline and a gate. It does not prevent
breaking changes — it makes them deliberate, and requires that a consumer be told how to migrate
before the release goes out.

## Requirements

### Requirement: The public API surface has a committed baseline
The `lib` module SHALL carry a checked-in dump of its public API, produced by the build rather
than written by hand, so that any change to the surface appears as a reviewable diff in the same
commit as the change that caused it.

**Verified**: Kotlin 2.4.10 provides this without a new dependency. `kotlin { abiValidation { } }` registers `updateKotlinAbi`, `checkKotlinAbi` and `internalDumpKotlinAbi` on `:lib`, and `updateKotlinAbi` writes `lib/api/lib.api`. Confirmed by running both tasks; the mechanism and the two compiler messages that established it are recorded in this change's `notes.md`.

#### Scenario: The baseline is regenerated by the build
- **WHEN** a contributor runs the dump task
- **THEN** the baseline file is rewritten from the compiled output
- **AND** no part of it is authored by hand

#### Scenario: Re-dumping is a deliberate act
- **WHEN** the public API has legitimately changed
- **THEN** updating the baseline is a separate, explicit command
- **AND** the updated baseline is committed alongside the change that caused it

### Requirement: A diverging API fails the build
The build SHALL fail when the compiled public API of `lib` no longer matches its committed
baseline, and that check SHALL run in CI on every pull request rather than only on a developer's
machine.

**Verified**: `checkKotlinAbi` inserts itself into `:lib:check` — `:lib:check --dry-run` lists `:lib:internalDumpKotlinAbi` and `:lib:checkKotlinAbi`, and on 2026-11-10 `./gradlew check -x :e2e-tests:test --dry-run` listed both. **Verified** that CI runs it: the `unit-tests` job runs `check`, a required status check of the main ruleset. Until `subtract-build-overhead` a second job, `api-baseline`, ran `./gradlew :lib:checkKotlinAbi` on its own; it closed a gap only while `unit-tests` ran a hand-picked task list, which ended on 2026-10-31. **Assumed** for the removal: *wrong if* a public declaration added to `lib` without re-dumping the baseline leaves `./gradlew check -x :e2e-tests:test`, the command `unit-tests` runs, green. Task 1.4 of `subtract-build-overhead` makes that observation.

#### Scenario: An undeclared API change is rejected
- **WHEN** the public API of `lib` differs from the committed baseline
- **THEN** the check task fails
- **AND** the failure names the divergence

#### Scenario: The gate runs on a pull request
- **WHEN** a pull request changes the public API without updating the baseline
- **THEN** the `unit-tests` job fails
- **AND** the pull request cannot be merged on that basis alone

### Requirement: What the check detects is stated honestly
The specification SHALL record both what the baseline diff catches and what it does not, so that
nobody relies on it for a guarantee it does not give.

It SHALL record that the check detects:

- the removal of a public declaration, including a single enum entry;
- any change to a function's JVM descriptor, including a change in the number or types of its
  parameters, on both the function and its synthetic `$default` overload.

**Verified by measurement**: both probes recorded in `notes.md`: inserting `dummyProbe: Boolean = false` between `center` and `end` on `daisyTooltip` changed `ZZZZZZZZ` to `ZZZZZZZZZ` in the descriptor of the function and of `daisyTooltip$default`; deleting `TooltipVariant.Error` removed the line `public static final field Error Lio/github/ollin/kdaisyui/components/TooltipVariant;`.

#### Scenario: A removed enum entry is caught
- **WHEN** a regeneration drops an enum entry from the public API
- **THEN** the baseline diff shows the entry's line removed
- **AND** the check fails until the baseline is deliberately updated

### Requirement: What the check does not detect is stated
It SHALL record that the check does **not** detect where in a signature a parameter was added,
because parameter names are not part of an ABI. Inserting a parameter mid-signature and appending
one produce the same diff.

**Verified by measurement**: the `daisyTooltip` probe recorded under the requirement above and in `notes.md`.

#### Scenario: A shifted parameter list is caught, without being localised
- **WHEN** a regeneration adds a parameter to an existing generated function
- **THEN** the baseline diff shows the changed descriptor
- **AND** the specification does not claim the diff identifies the parameter's position

### Requirement: A breaking change carries a migration note before release
A public API change identified as breaking SHALL have a **How to migrate** entry in
`docs/upgrading.md` before the release that ships it, and the release documentation SHALL treat the API check and
that entry as part of what "ready to tag" means.

**Verified**: `README.md` already carries a "How to migrate" section for 0.2.0, written after the fact, which is the shape the rule generalises. **Assumed:** that this remains a documented rule rather than an automated one. *Wrong if:* a release ships a breaking change without the entry, which would show that a rule nothing enforces is not a rule.

The entries lived in `README.md` until `move-migration-guides` (2026-11-01) moved them to
`docs/upgrading.md`, which README links.

#### Scenario: A reader of a breaking release can act on it
- **WHEN** a release removes or changes a public declaration
- **THEN** `docs/upgrading.md` explains what to change at the call site
- **AND** the entry exists before the tag is pushed, not after
